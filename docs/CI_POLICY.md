# Ускоренная приёмка CreatePortal 2.0

Решение владельца от 16.11.2026: минимизировать проверки, ускорить разработку. Для обычной задачи достаточно **зелёного релевантного CI** по актуальному SHA PR.

## Базовый путь
1. Исполнитель работает в своей ветке и открывает PR.
2. Автоматический CI проверяет затронутые части проекта. Если CI зелёный и нет очевидного нарушения разрешённой зоны файлов, директор может принять работу и слить PR в рамках одобренных полномочий.
3. Если CI красный, исправить ошибку и повторить только нужную проверку. Если CI отсутствует, отменён, запущен на устаревшем SHA или нет соответствующего job, зелёного сигнала нет.
4. Отчёт: ссылка на PR и краткое описание (1–3 предложения). Без обязательных скриншотов, видео, PDF, отчётов о каждом тесте или заданных квот количества тестов.

## CI минимального объёма
Линтер/синтаксис, проверка сборки изменённого компонента, релевантные автоматические тесты; запрещены повторные запуски одних и тех же наборов без причины. Не запускать Android release/APK или end-to-end, если PR не касается этих частей. Использовать path filters, кэш зависимостей, отмену устаревших прогонов.

## Защитные исключения
Не ослаблять критические инварианты денег/транзакций, авторизацию, сохранность данных, миграции БД, токены/ключи, HMAC вебхуков. Для деплоя VPS, публикации релиза, удаления данных, смены разрешений, ключей и денежных операций нужны предусмотренные явные согласования владельца независимо от зелёного CI. Не отключать секрет-сканирование и проверки доступа. Ручные визуальные проверки возможны лишь при конкретном дефекте UI, без требования хранить снимки в PR.

## Не делать
Не требовать по умолчанию четыре набора скриншотов для тем/разрешений, 40–60 новых тестов на пакет, ручной дубль CI, отдельный отчёт QA или прогон всех workflow репозитория для локальной правки.
